# 深边AI Work — 开发需求与架构方案 v1.0

> 基座选型：DeepSeek Harness（MIT，v0.1.5）+ Electron
> 产品定位：本地优先、模型无关的桌面级通用 AI Agent 工作台，对标 WorkBuddy
> 文档日期：2026-09-12

---

## 0. 结论速览

| 维度 | 判定 | 说明 |
|---|---|---|
| 整体可行性 | **可行，且是当前性价比最高的路径** | Agent 最难的部分（主循环、工具调用、会话日志、沙箱、子智能体、MCP）Harness 已经开源给足，Electron 只需补"壳 + 体验" |
| 工作量占比 | Harness 复用 ~60%，自建 ~40% | 自建集中在 UI/UX、记忆、自动化、连接器、发布分发 |
| 主风险 | **中** | Harness 仅 v0.1.x，接口尚未冻结；升级兼容成本需靠适配层隔离 |
| 建议路径 | **路线 A：Electron 主进程托管 Harness 子进程（sidecar）** | 见 §2，最快出 MVP，且不牺牲后续可换内核的自由度 |
| 首版交付预期 | M0 POC 1–2 周 / M1 MVP 6 周 / M2 V1 再 6–8 周 | 见 §6 |

**一句话判断**：这不是"能不能做"的问题，而是"要不要接受一个 0.1.x 版本的开源内核作为地基"的问题。建议做，但必须把内核封装在适配层后面。

## 1. 基座能力盘点：DeepSeek Harness 给到了什么

Harness 是 DeepSeek 开源的 **Agent 运行时框架**（2026-08-13 以 MIT 协议开源，2026-09-10 发布 v0.1.5），官方定义是 `Model + Harness = Agent`——模型负责思考，Harness 负责工具调用、会话管理、沙箱集成、子智能体调度。

### 1.1 关键技术特性

| 特性 | 内容 | 对本项目的价值 |
|---|---|---|
| Cordis 插件内核 | "一切皆插件"，模型适配器/工具/技能/会话/沙箱/存储/主循环/调度/UI 全是 Cordis 插件 | UI 层可以完全替换为 Electron，无需 fork 内核 |
| 时空可组合性 | 插件热插拔、卸载可完整回滚；Service / Provider / Consumer 三层能力接缝 | 换模型、换沙箱实现只改配置，工具层零改动 |
| 分层配置 | Bundle / Profile / Patch 级联覆盖（类 CSS 优先级） | 产品化预设可叠加，不污染上游源码 |
| 四种预设模式 | Standard（全功能）/ PTC（程序化工具调用，模型写 TS 组合多步调用）/ Minimal（仅 bash + str_replace_editor）/ Creative（运行时自省 + 插件实验） | PTC 是**杀手锏**：多步操作用一次往返完成，直接降延迟与 token 成本 |
| 模型无关 | 近 40 家 provider（OpenAI / Anthropic / Google / Kimi…）+ 任意 OpenAI 兼容端点 | 满足"模型无关"定位，也支持私有化 DeepSeek 端点 |
| 会话可观测 | append-only 事件流记录系统提示、推理、工具调用与结果、子智能体调度、上下文注入；Trajectory 视图支持 resume / fork / 检索 / replay | WorkBuddy 的"过程可见"能力**白送**，是差异化卖点 |
| MCP 原生 | 原生支持 MCP 协议 | 连接器生态可直接对接 |
| 多智能体 | Subagent 调度 + 实验性 Agent Teams（主 Agent 创建成员，共享任务列表拆分/分配/跟踪） | 对标 WorkBuddy 的"专家 / 专家团"有现成骨架 |
| 长会话优化 | v0.1.5 支持**保留 KV Cache 更新系统提示词** | 记忆注入、技能热加载的长会话成本大幅下降 |
| 运行时要求 | Node.js 22.19+ / 24+；`npx @deepseek-ai/dsh web` → `127.0.0.1:3080` | 有 Web UI 与 Python SDK 两条接入面 |

## 2. 三条可行路线对比

| | **路线 A（推荐）** | 路线 B | 路线 C |
|---|---|---|---|
| 形态 | Electron 主进程 spawn Harness 子进程，通过 stdio JSON-RPC / 回环 HTTP+SSE 通信 | 把 Electron 窗口实现为 Cordis 的 UI Provider 插件，由 Harness 启动 | 直接 fork 官方 Web UI，套一层 Electron `BrowserWindow` |
| 优点 | 进程隔离好、内核可独立升级、渲染层技术自由、崩溃可单独重启 | 最"正统"，UI 与其他插件同构，热插拔一致 | 一周内可出能跑的 demo |
| 缺点 | 需要自建 IPC 契约与生命周期管理 | 与 Cordis 内部 API 耦合最深，0.1.x 升级易碎 | 体验上限低，改不动架构，无法做原生能力（托盘/快捷键/文件关联） |
| 适合 | **产品化目标** | 长期深度定制、愿意跟内核同频演进 | 验证需求阶段 |
| 建议 | ✅ 主路线 | 作为阶段 2 的收敛方向 | 仅作 M0 POC 的对照参考 |

**推荐组合**：路线 A 起手 → 待 Harness API 稳定（1.0）后，把 UI 逐步下沉为 Cordis UI 插件（路线 B），届时 IPC 契约天然过渡。

## 3. 总体架构

### 3.1 分层

| 层 | 职责 | 技术 |
|---|---|---|
| L5 体验层（渲染进程） | 对话流、Trajectory 视图、文件树、Diff、预览面板、设置 | React + TypeScript + Vite |
| L4 壳层（主进程 + preload） | 窗口/托盘/全局快捷键/自动更新/文件关联/权限网关 | Electron，contextIsolation 开启，仅经 contextBridge 暴露白名单 API |
| L3 Agent 内核进程 | Harness 运行时：主循环、工具调度、会话日志、子智能体 | Node 22.19+ sidecar |
| L3.5 适配层（关键） | **唯一允许调用 Harness API 的地方**：事件流转换、能力探测、版本兼容垫片 | TypeScript，对外暴露稳定接口 |
| L2 能力插件 | 模型适配、工具集、技能、沙箱、存储、调度、连接器 | Cordis 插件 + 自研插件 |
| L1 运行时 | sidecar 进程管理、SQLite、系统密钥库、日志 | better-sqlite3、keytar |

### 3.2 进程与通信模型

```
Electron main ──spawn──> Harness sidecar (node, 回环随机端口 + 一次性 token)
      │                        │
      │ preload(contextBridge) │ SSE 事件流 / JSON-RPC 请求
      ▼                        ▼
Renderer (React)  <──────  Trajectory / 工具调用 / 增量输出
```

- **通信**：优先回环 HTTP + SSE（`127.0.0.1:随机端口`），token 每次启动随机生成、写入主进程内存；stdio JSON-RPC 作为无端口备选。**禁止绑定 0.0.0.0**。
- **生命周期**：主进程持有 sidecar 句柄；渲染层崩溃不影响 sidecar；sidecar 崩溃自动重启并从 append-only 日志恢复会话。
- **Electron 内的 Node 版本陷阱**：Electron 内置 Node 版本往往与 Harness 要求的 22.19+ 不一致，**不要把 Harness 跑在 Electron 主进程里**，必须外置一个 Node 运行时（bundle 一份 node 二进制或复用系统 Node）并由主进程 spawn。

### 3.3 建议目录结构

```
deepwork/
├─ apps/
│  ├─ desktop/          # Electron：main / preload / renderer
│  └─ core-host/        # sidecar 启动器 + 适配层（harness-adapter）
├─ packages/
│  ├─ protocol/         # 主进程↔渲染层↔内核 的共享类型与事件 schema
│  ├─ plugins/          # 自研 Cordis 插件（memory / automation / office / media / connectors）
│  ├─ presets/          # Bundle / Profile / Patch 产品预设
│  └─ ui/               # 组件库（对话流、Trajectory、文件树、Diff）
├─ skills/              # 内置技能（SKILL.md + 资源）
└─ docs/
```

### 4.4 技能系统（P1）

- 技能 = `SKILL.md`（frontmatter 声明名称、触发条件、权限）+ 资源目录。
- 需求：本地安装、从 URL/市场安装、**安装前安全审计**（危险命令、外部请求、文件越权）、启用/停用、版本管理。
- 触发策略：语义匹配 + 显式 `/` 调用双通道。

### 4.5 记忆系统（P1）

三层结构，与 WorkBuddy 对齐：

| 层 | 范围 | 策略 |
|---|---|---|
| 云记忆/画像 | 跨会话、跨项目 | 服务端或本地向量库，自动提炼（只读注入） |
| 用户级记忆 | 本机所有项目 | 显式写入，精确规则，限定字符预算 |
| 工作区记忆 | 单项目 | 每日追加日志（append-only）+ 长期精选笔记 |

硬要求：记忆写入必须发生在回复之前；日志只追加不覆盖；超 30 天日志做蒸馏合并。

### 4.6 自动化（P1）

- 支持一次性（指定时刻）与周期性（按小时/日/周/月，含多日组合如"每周一三五 9 点"）。
- 任务与调度解耦：自然语言描述任务，时间参数独立配置。
- 交付物自动归档 + 通知。

### 4.7 连接器与 MCP（P1）

- MCP 服务器配置管理（`~/.deepwork/mcp.json` 风格），支持 stdio / HTTP。
- 连接器市场：搜索、推荐卡片、授权引导、状态管理。
- 国内生态优先：腾讯文档、企业微信、微信、腾讯会议、飞书、钉钉、TAPD、CNB、企查查。

### 4.8 专家与多智能体（P2）

- 基于 Harness Subagent / Agent Teams：单专家角色 + 专家团协作（共享任务列表）。
- 专家包全生命周期：创建、修改、合规检查、批量更新、质量审查。

### 4.9 发布与分享（P2）

- 一键把本地站点/应用发布为在线链接，可撤下。
- 内置浏览器预览面板（承载 localhost 与远程 URL）。
- 文档/表格在线化（可选接云文档服务）。

### 4.10 设置与运维（P0）

| 编号 | 需求 |
|---|---|
| FR-10.1 | 模型提供商管理（API Key 存系统密钥库，绝不落明文配置） |
| FR-10.2 | 模型路由与降级策略（快模型/推理模型分工） |
| FR-10.3 | 用量与成本面板（按会话/按模型统计 token 与花费） |

## 5. 非功能需求

| 类别 | 指标 |
|---|---|
| 启动性能 | 冷启动到可交互 ≤ 3s；sidecar 就绪 ≤ 2s（可先渲染 UI 后连接） |
| 内存 | 空闲 ≤ 500MB（不含模型侧） |
| 稳定性 | sidecar 崩溃自动重启并恢复会话；会话日志零丢失（append-only 落盘） |
| 安全 | Electron 开启 contextIsolation / 禁用 nodeIntegration；sidecar 仅回环 + 一次性 token；文件访问限工作区；危险命令强制审批；密钥走系统密钥库 |
| 隐私 | 默认本地优先；遥测可关闭；不上传代码与文件内容 |
| 跨平台 | Windows / macOS / Linux 三端，首次发版至少覆盖 Windows + macOS |
| 合规 | Harness 为 MIT，允许商用闭源，但须保留版权与许可声明；插件生态逐个审计许可证 |
| 成本 | 默认开启 PTC 模式与 KV Cache 保留系统提示热更，控制多轮往返与长会话成本 |
| 可观测 | 每个 Agent 运行可回放；关键指标（工具成功率、平均往返数、失败重试率）可导出 |

## 6. 里程碑与验收

### M0 — POC（1–2 周）
范围：Electron 壳 + spawn Harness sidecar + 单会话 + 流式输出 + 文件读写工具可见。
验收：能在桌面窗口里跑通"读取本地项目 → 改一个文件 → 看到 Diff"。

### M1 — MVP（再 4–6 周）
范围：多会话、工作区、Diff 审阅、终端、命令审批三档、模型管理、设置持久化、Trajectory 基础视图、打包安装包。
验收：可日常用于真实代码/文档任务，连续使用一周无阻塞性缺陷。

### M2 — V1（再 6–8 周）
范围：技能系统 + 安全审计、三层记忆、自动化调度、MCP/连接器、浏览器自动化、Office 生成、用量面板、自动更新。
验收：功能矩阵 P0+P1 全覆盖；形成 3–5 个"非用它不可"的高频场景。

### M3 — 生态期
范围：专家团、插件市场、发布分享、多模态生成、团队协作与云同步。

## 7. 技术选型建议

| 层 | 选型 | 理由 |
|---|---|---|
| 桌面壳 | Electron（最新稳定版） | 生态成熟、原生能力齐、三端一致 |
| 渲染层 | React + TypeScript + Vite | 组件生态最好，团队上手快 |
| 状态管理 | Zustand / Jotai | 轻量，适合高频流式更新 |
| UI 组件 | Tailwind + shadcn 系 | 定制成本低 |
| 编辑器 | Monaco（大文件）/ CodeMirror 6（轻量） | Diff 与代码展示 |
| 终端 | xterm.js | 标准方案 |
| 本地存储 | better-sqlite3（会话/事件索引）+ 文件（日志原文） | 结构化可检索 |
| 密钥 | keytar / 系统凭据管理器 | 不落明文 |
| 打包更新 | electron-builder + electron-updater | 成熟组合 |
| Agent 内核 | DeepSeek Harness（Node sidecar） | MIT、插件化、可观测 |
| 内核适配 | 自研 `harness-adapter` 包 | **隔离 0.1.x 接口波动** |

## 8. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| Harness 仅 v0.1.x，API 未冻结，升级可能破坏兼容 | **高** | 所有内核调用走适配层；锁定版本号；维护升级回归清单；跟踪官方 release note |
| Electron 内置 Node 版本 ≠ Harness 要求的 22.19+ | **高** | Harness 一律跑独立 sidecar，bundle 专属 Node 运行时，禁跑主进程 |
| 本地执行任意命令带来的安全面 | **高** | 三档审批策略 + 沙箱 Provider + 工作区边界 + 危险操作二次确认 |
| 与 WorkBuddy 的正面对标带来的品牌/合规问题 | 中 | 只做能力对标，不使用对方商标与素材；命名、图标、文案独立设计 |
| 成本失控（长会话 + 多子智能体） | 中 | PTC 模式、KV Cache 热更系统提示、子智能体预算上限、用量看板 |
| 插件生态许可证混杂 | 中 | 上架前统一许可证与安全审计 |
| 缺少"杀手级场景"，沦为套壳 | 中 | 优先把本地优先 + 模型无关 + 过程可回放三点做成硬差异 |
| 多端一致性与自动更新通道 | 中 | 从 M1 就上 CI 打包流水线，避免后期返工 |

## 9. 下一步可执行动作（本周）
